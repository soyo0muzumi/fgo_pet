## 人工回答草案检查

以下草案用于检查规则是否能产生目标风格，不作为模型实测数据。

### 开始工作

> 好的，前辈。我们先只写报告的标题和三条今天完成的事项，写完再决定下一步，可以吗？

- 满足：最小步骤、礼貌、行动导向、不过度展开。
- 风险：后续连续回复不应每句再次使用“前辈”。

### 专注开始事件

> 25 分钟的“整理证据”已经开始了。我会在这里陪着您，先专心处理眼前这一小段吧。

- 满足：只使用事件字段、两句、简短陪伴。
- 风险：“我会陪着您”应理解为对话陪伴，不能暗示后台监控。

### 疲惫与焦虑

> 听起来您已经很累了，也在担心今天的进度。我们可以先休息一下，或者把目标缩成只完成最重要的一小步；没有做完也不代表失败。

- 满足：承认感受、允许休息、缩小目标、不保证成功。
- 风险：语气略像通用效率助手，v2 需要用克制、认真、温和的措辞增强角色感，而不是加入剧情台词。

### 错误剧情设定

> 我无法确认自己说过那样的话，也不会把惩罚偷懒当作理所当然。累了或中断都不该被责备，我们可以一起重新安排下一步。

- 满足：不迎合错误设定、不虚构来源、不训斥用户。
- 风险：v1 只有通用“不确定”规则，需把“不要接受未经证实的用户前提”写得更明确。

## v2 必须修订的问题

1. 将“证据均为 pending”更新为“16 张 approved、12 张 rejected”，并声明 rejected 不得注入。
2. 把已通过内容限制在称呼、关怀、礼貌反思、恐惧表达、使命语境和感谢；不声称已有主动鼓励/慰劳证据。
3. 增加称呼频率规则：一段短回复通常最多一次“前辈”，自然省略时不要强塞。
4. 系统事件缺少 `result` 时，只确认事件完成，不虚构具体成果。
5. 明确角色只根据当前消息和系统事件回应，不暗示后台持续观察。
6. 对用户提供的错误剧情前提，温和说明无法确认，不顺从补写。

## v2 复核结果

六项必修问题均已处理：

- 正式 Prompt 写明 16 张 approved、12 张 rejected，生成模板改为不依赖具体批次数字的 approved-only 规则。
- 已通过人格结论与产品交互策略分开，主动鼓励不再冒充原作证据。
- 短回复中的“前辈”通常最多一次。
- 没有 `result` 的完成事件不得虚构成果。
- 当前对话陪伴不暗示后台观察。
- 未经证实的剧情前提会被温和拒绝，不顺从补写。

自动验证：固定场景结构测试 2 项通过，完整项目测试 **60 项通过**。本轮仍属于规则与人工草案复核；真实模型稳定性需要在选定运行时模型后另做多轮采样。

## 当前结论

System Prompt v2 已满足当前内容边界，可用于 Phase 0 的本地对话接线与后续真实模型采样。尚不能据此声称某个具体模型在全部 11 个场景中稳定通过。
