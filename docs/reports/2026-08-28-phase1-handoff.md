## 1. 状态判定

Phase 1 的正式 WPF 桌宠壳和扩展包运行时已经实现，当前版本可用于继续开发
Phase 2。用户完成了主设备上的连续实机复核，并确认本轮发现的角色包扫描、附着面板、
点击拖动、四边边缘保护和托盘交互问题均已修复。

本报告不把 Phase 1 标为“可发行”，原因如下：

1. `docs/testing/phase1-windows-matrix.md` 尚未逐项补齐 200%、150% 和混合 DPI 的正式证据；
2. 玛修角色包仍是开发/预览输入，需要结合 Phase 2、Phase 3 的资源需求重新设计后再发行；
3. 独立 P1.4 Python 打包 SDK 只完成前两个基础任务，且后续实现应等待角色包新合同确定；
4. 本项目已明确暂不发布任何程序包或角色包，待计划功能整体完成后统一发行。

因此应使用以下状态词：

- Phase 1 主程序：`implementation-complete`
- Phase 1 工程交接：`ready`
- Phase 1 正式验收：`pending-manual-matrix`
- 程序/角色包发行：`deferred`

## 4. 明确不属于 Phase 1 的运行时能力

以下能力不得因为已有内容素材而误报为 Phase 1 已实现：

- LLM 对话、Prompt 执行、结构化模型输出；
- 长期记忆和短期对话摘要；
- 剧情知识运行时检索；
- 事件中心、番茄钟、时间线和羁绊结算；
- Codex 插件、事件桥和离线队列；
- 应用感知、备份迁移、安装包和首次使用引导。

Phase 1 安装器允许保存 JSON、Markdown 和纯文本 Persona 资源，但当前应用不解释或执行
这些资源。这是刻意的安全边界，不是缺陷。

## 5. 角色资源包重构交接

### 5.1 当前结论

不发布现有 `mash-preview.fgopetpack`。它仅用于 Phase 1 安装、扫描、切换和画像实机验证，
不能作为 `official.mash 1.0.0`。

角色包需要从“美术归档”重构为可跨阶段演进的声明式内容容器，但仍必须保持纯资源、
无代码、不可执行。程序包与角色包继续分别构建、版本化和发行。

### 5.2 建议的跨阶段分层

```text
official.mash/
├─ package.json                 # 身份、版本、兼容范围、能力声明
├─ previews/                    # 从者库及发行预览
├─ appearances/                 # Phase 1：画像、表情、合成几何
├─ dialogue/                    # Phase 2：本地事件台词与表情倾向
├─ persona/                     # Phase 3：资料卡、Prompt、风格规则
├─ knowledge/                   # Phase 3：approved-only 摘要与来源索引
├─ codex/                       # Phase 4：声明式事件反馈规则，不含工具代码
└─ localizations/               # 跨阶段本地化
```

上述目录是后续设计输入，不是已经批准的新 schema。正式实现前必须单独评审：

- `package.json` 的 capability/version 协商；
- Persona 与知识文件的独立 schema；
- 第三方 Prompt 低信任隔离，不能覆盖应用安全规则、权限或隐私边界；
- 完整剧情正文不得入包，只允许 approved 摘要、来源定位和必要索引；
- Phase 2/3 未启用的目录必须能够安全保存并被旧版本忽略；
- 包升级、迁移和向后兼容策略。

## 6. 后续阶段入口

### Phase 2：事件、番茄钟与时间线

Phase 2 可以直接建立在当前主程序之上，优先顺序建议为：

1. 定义统一事件模型、优先级、打断、合并、冷却和去重；
2. 实现可恢复番茄钟及本地状态持久化；
3. 将静态 Todo/Dialogue 面板替换为真实 ViewModel 数据流；
4. 建立今日时间线和只结算一次的轻量羁绊；
5. 定义角色包 `dialogue/` 声明式合同，但继续提供无角色台词时的本地默认回退。

### Phase 3：对话与记忆

复用现有内容管线成果，但不要直接复用原始剧情缓存作为发布内容：

- `system-prompt.md`、资料卡和说话风格是候选输入；
- 只允许 approved 证据进入运行时；
- 普通对话不加载剧情层，用户主动询问剧情时才检索；
- 检索返回少量摘要和来源定位，不注入完整脚本；
- 第三方 Prompt 必须位于应用安全与能力边界之下；
- API Key 进入 Windows Credential Manager，不进入角色包、设置、日志或备份。

### Phase 4/5

- Phase 4 才接入 Codex Skill/MCP、本地事件桥、离线队列和跳转；
- Phase 5 完成应用感知、收藏、备份迁移、安装包、首次使用引导与最终分发；
- 程序和角色包在所有目标功能与迁移策略稳定后统一准备首个公开 Release。

## 8. 交接结论

后续开发可以从 Phase 2 开始，不需要等待玛修角色包发行，也不应在 Phase 2 提前实现
Phase 3 的 Prompt/剧情执行。Phase 1 主程序应进入稳定维护状态，只接受阻塞后续阶段的缺陷、
安全问题和实机矩阵修复。

在这些动作完成之前，项目状态应保持“工程交接完成，发行未批准”。
