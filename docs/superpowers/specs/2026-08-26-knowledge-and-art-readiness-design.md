# FGO Pet 知识与美术前置设计

日期：2026 年 8 月 26 日

## 背景与阶段门槛

Phase 0 暂不启动。进入下一阶段前必须完成三个前置项：角色资料卡知识层、按需剧情检索层、默认常服美术处理管线。

现有 `D:\fgo_unpack\fgo_assets\servant\000001\nice.json` 与 `servant\800100\nice.json` 都是未启用 lore 的基础 payload，包含数值与资源索引，但没有 `profile`。仓库内 `fgo-game-data-api` 已支持 `lore=true`，并定义了 `NiceLore.comments`；因此资料卡任务必须先取得 lore-enhanced payload，不能误把当前 `nice.json` 当成完整资料卡。

## 总体架构

系统使用三层知识和一条独立美术管线：

1. **资料卡事实层**：常驻、概括、来源明确，回答身份与一般设定。
2. **剧情检索层**：用户询问具体剧情时按需召回少量相关场景。
3. **回答编排层**：默认先用 2–4 句回答，再按用户意愿展开。
4. **美术资产层**：将指定合图确定性切分为全身立绘、28 个表情与运行时 manifest。

所有产物仍以 `servant_id=800100`、`collectionNo=1` 为同一角色身份，不因文件夹 `000001` 与 `800100` 的不同编号方式产生两份角色。

## 子系统 A：资料卡事实层

### 输入

- 首选：官方中文、`lore=true` 的玛修资料卡 payload。
- 回退：官方日文 lore payload；生成中文摘要时保留日文原文和 `jp_fallback`。
- 基础身份与美术索引：当前本地 `nice.json`。

### 提取范围

- 角色 ID、图鉴编号、姓名、职阶、性别、稀有度等稳定身份字段。
- `profile.comments` 中公开的人物简介、设定与分阶段资料。
- 每条资料的解锁条件、来源地区、原始语言和原始顺序。
- 不把技能数值、战斗倍率或卡面参数混入人格摘要，除非用户明确询问游戏机制。

### 输出

`character-profile.json`：

- `identity`：稳定身份字段。
- `facts[]`：原始资料条目、中文摘要、来源语言、解锁条件、权威等级。
- `compact_summary`：常驻上下文摘要，目标 300–600 tokens。
- `source_hash`：上游 payload 哈希，用于判断是否需要重建。

资料卡是一般角色事实的第一来源，但不能覆盖剧情中明确的阶段差异。

## 子系统 B：剧情检索层

### 索引结构

- 使用现有 904 份结构化剧情 JSON，不复制完整正文进 Git。
- 建立本地 SQLite FTS5 索引，最小记录单位为场景中的单条台词，同时保存篇章、script ID、scene index、order、speaker 与语言。
- 额外建立篇章/脚本目录项，保存标题、角色命中、关键词和可展示的短摘要。
- 可选语义重排器通过接口接入；不可用时必须退回 FTS 结果，不能让剧情问答整体失效。

### 查询路由

- “玛修是谁、性格怎样”等概括问题：优先资料卡层。
- “某一章发生了什么、她为什么这样做”等剧情问题：检索剧情层。
- 同时包含设定和剧情的问题：先用资料卡给稳定结论，再用剧情片段说明阶段或例外。

### 召回与上下文预算

1. 关键词规范化：角色别名、篇章别名、简繁体和中日文名称映射。
2. FTS 召回候选台词，按篇章、说话人、邻近命中和玛修直接发言加权。
3. 对前若干候选展开同场景相邻台词，合并重叠窗口。
4. 可选语义重排后只注入 2–4 个窗口。
5. 默认剧情上下文上限 900 tokens；用户要求继续展开时再执行下一轮检索，而不是一次加载全部资料。

### 回答策略

- 默认先给 2–4 句直接答案。
- 有可靠命中时不得笼统回答“不清楚”；应根据资料卡和检索片段作答。
- 命中不足时准确说明缺少的范围，例如“当前索引没有覆盖该活动”，而不是伪装失忆。
- 回答结尾可简短询问是否需要展开具体章节、前因后果或原文出处。
- 不大段复制原作台词；必要时只使用短引并保留内部来源定位。

## 子系统 C：回答编排层

模型每次最多接收：

1. 常驻资料卡摘要。
2. 当前问题的路由结果。
3. 最多 2–4 个剧情窗口。
4. 当前任务状态与短期记忆。

回答编排器必须区分三种状态：

- `answered_from_profile`：资料卡已足够。
- `answered_from_story`：使用剧情检索结果。
- `coverage_gap`：本地语料确实未覆盖，并明确缺失范围。

该状态仅供应用调试和测试，不直接暴露内部路径、索引或 Prompt。

## 子系统 D：美术资产管线

### 固定输入

`D:\fgo_unpack\fgo_assets\servant\000001\98001000_merged.png`

原图尺寸为 1024×2560，格式为 32-bit ARGB，包含：

- 上部一张常服全身立绘。
- 下部 7 行 × 4 列，共 28 个表情格。

### 处理原则

- 原图只读保留，不覆盖、不重采样。
- 对全身立绘与 28 个表情先生成未经抠图的原始切片，作为回退与视觉校验基准。
- 对每个切片从边缘执行连通背景移除；使用颜色容差与边缘去色，不能按单一 RGB 值全局删除，以免误伤头发、阴影和衣服。
- 输出统一透明 PNG，不使用生成式重绘，不补画被裁掉的身体部分。
- 全身立绘记录脚底锚点；表情记录眼睛中心、嘴部中心和头部包围盒，供 WPF 对齐。

### ID 与 manifest

- 28 个表情使用稳定坐标 ID：`r01c01` 至 `r07c04`。
- 语义标签单独记录，可一格多标签，不用主观标签替代坐标 ID。
- Phase 0 常用别名至少包括 `neutral`、`smile`、`happy`、`concerned`、`surprised`。
- 其余表情全部处理并保留，可标记为流泪、受伤、愤怒、喊叫等强情绪，但默认日常状态不自动调用。
- manifest 保存源文件哈希、切片矩形、透明包围盒、锚点、标签和输出相对路径。

### 输出目录

仓库外生成目录：

`D:\fgo_unpack\fgo_assets\pet\mash\casual\`

建议结构：

- `source-manifest.json`
- `body/full.png`
- `expressions/raw/rXXcYY.png`
- `expressions/transparent/rXXcYY.png`
- `expression-manifest.json`
- `qa/contact-sheet.png`

## 错误处理与可恢复性

- lore payload 缺少 `profile` 时立即失败并提示必须使用 `lore=true`，不生成空资料卡。
- 索引记录与原剧情文件哈希不一致时，只重建受影响脚本。
- 语义重排器不可用时自动降级至 FTS，不返回空答案。
- 美术切片数量不是 28、透明前景触边或人物面积异常时停止发布产物，并生成 QA 报告。
- 每次生成写入临时目录，全部校验通过后原子替换正式产物。

## 测试与验收

### 资料卡

- lore payload 能提取 profile comments、语言和解锁条件。
- 无 profile 的当前 nice payload 被明确拒绝。
- 中文优先，日文回退带 `jp_fallback` 与原文。
- compact summary 在预算内且不包含战斗数值噪声。

### 剧情检索

- 用已知篇章、角色和台词关键词能召回正确 script/scene。
- 别名与简繁体查询仍有命中。
- 最终只注入 2–4 个窗口且不超过预算。
- 无语义组件时 FTS 路径仍可回答。
- 真正无覆盖时返回具体 `coverage_gap`，不返回伪造剧情。

### 美术

- 精确生成 1 张全身立绘和 28 张原始/透明表情。
- 所有透明 PNG 尺寸、Alpha 通道、锚点和 manifest 一致。
- 人物前景没有被背景移除算法明显侵蚀。
- contact sheet 可人工核对全部表情。
- WPF 在 100%、125%、150%、200% 缩放下边缘清晰且锚点稳定。

## 下一阶段准入条件

只有以下全部满足，Phase 0 才从 `BLOCKED` 改为 `GO`：

1. 资料卡 facts 与 compact summary 已生成并审核。
2. 剧情检索对代表性问题能给出简答并按需展开。
3. 900-token 上下文预算与 coverage gap 行为通过测试。
4. 常服全身立绘和全部 28 个表情处理完成并通过 contact sheet 审核。
5. 相关自动测试和人工视觉检查全部通过。
