# FGO Pet Phase 5：首版产品化与长期可用性设计

日期：2026-09-01

状态：已确认（2026-09-01）

前置：Phase 4 已在主要 Windows 环境验收，并合入本地 `main`；公开发布不在本设计授权范围内。

## 1. 决策

Phase 5 定义为**首版产品化与长期可用性阶段**，而不是新功能扩张阶段。目标是把 Phase 1–4 已完成的桌宠、专注、对话、记忆、Todo 和 Agent 集成变成可长期使用、可恢复、可安装升级的产品。

推荐交付顺序：

1. Phase 5.1：任务运行安全；
2. Phase 5.2：版本化备份与事务恢复；
3. Phase 5.3：配置引导；
4. Phase 5.4：角色包与安装候选；
5. Phase 5.5：小范围试用与发行门禁。

首个实现切片是“派发结果核对 + 执行记录安全归档”。在该切片通过前，不新增应用感知、收藏或新的 Agent 奖励来源。

## 2. 当前基线与问题

Phase 4 closeout 已验证完成事件投影、Relay/Adapter 重启、撤销后重新批准以及数据库最终完成态。合入后的 Release 构建、.NET 697 项和 Python 105 项测试均通过。Phase 5 功能尚未实现。

当前交付缺口是：

- 网络超时后，App 只能保留“派发结果未知”的安全预留，用户缺少核对入口；
- Adapter journal 上限为 512 条，Relay dispatch receipts 和 task watermarks 各为 4096 条；耗尽时会安全拒绝，但没有面向用户的归档与容量恢复流程；
- 常用目标注册、项目选择和配对仍存在 CLI 与不透明 ID 操作；
- `UserDataExportService` 只导出允许分享的数据，不含专注、完整运行状态和设置，也没有恢复能力；
- `.fgopetpack` 安装器已存在，但独立 SDK 分支、确定性 builder、正式玛修候选包和发行安装链路尚未闭合；
- 完整安装 smoke、升级/卸载重装、设备范围和发行验收仍待完成。

## 3. 目标与非目标

### 3.1 目标

- 用户能理解每个任务的当前状态、风险和可执行的下一步；
- 任何核对、归档、重试或恢复操作都不会重复创建真实 Agent 任务；
- 用户能从空数据目录恢复规定业务数据，失败时原数据保持可用；
- 常用 Agent 配置无需手改 JSON，权限仍为显式、最小授权；
- 同一角色包输入能生成相同内容哈希，并能安全安装、升级和回滚；
- 在明确支持的 Windows/x64 环境完成安装、离线使用、可选连接、升级、恢复与卸载闭环；
- 安装并激活角色包后，无模型或无 Agent 插件时，桌宠和专注功能仍能离线使用。

### 3.2 非目标

Phase 5 首版门禁不包含：

- 应用类别感知、窗口标题或屏幕采样；
- 礼装收藏和新的 Agent 羁绊奖励；
- 第二个 Agent 平台；
- 云同步、自动更新、商城、移动端；
- 后台自主记忆写入；
- 重做渲染、画像、主题或附着面板顶级导航；
- 公开上传、推送、远端合并或正式发布。

## 4. 总体架构

延续现有边界：

- `FgoPet.Core` 保存状态合同、备份清单和不依赖 IO 的决策规则；
- `FgoPet.Infrastructure` 负责 SQLite、设置文件、角色包和本地 Agent 管理的持久化实现；
- `FgoPet.App` 负责用户确认、停写协调、状态说明和恢复编排；
- `FgoPet.AgentProtocol` 只增加容量、核对和归档所需的版本化消息；
- Relay 与 Adapter 继续独立运行，凭据与用户业务备份分离；
- Python 内容 CLI 负责角色包构建和离线验证，.NET 安装器负责运行时安装判定。

所有新能力通过现有设置页、TODO 面板和安装工具接入，不增加顶级导航。各交付应能独立测试、独立回退，不把整个 Phase 5 做成一次大迁移。

## 5. Phase 5.1：任务运行安全

### 5.1 状态可理解与结果核对

App 将 Agent 执行状态映射为用户语义：

| 内部情况 | 用户状态 | 允许操作 |
|---|---|---|
| 尚未派发 | 计划中 | 编辑、确认派发 |
| 已发送且有远端任务身份 | 执行中 | 打开任务、取消等待 |
| 超时且远端结果未知 | 待核对 | 打开 Codex、复制任务/请求标识、手动确认结果 |
| 来源离线 | 等待连接 | 打开设置、稍后继续 |
| 权限失效或已撤销 | 需要授权 | 打开 Agent 连接设置 |
| 已完成/失败/取消 | 终态 | 查看历史、归档；不再重发 |

核对入口只读取已持久化的 `dispatch_request_id`、来源、目标和远端任务身份。若运行时不能可靠查询远端状态，则明确引导用户到 Codex 核对，不伪造自动恢复。用户发起“新尝试”必须生成新的 Todo 执行和新的请求 ID，并显示它与旧尝试的关系；普通刷新、重连和重启不得创建新任务。

### 5.2 容量与安全归档

新增只读容量快照，分别报告 App 执行记录、Relay receipts/watermarks 和 Adapter journal 的已用量、上限及最老可归档终态。容量状态通过现有 Agent 管理边界展示，不把 Relay/Adapter 本机状态直接暴露为可编辑文件。

归档只允许处理满足全部条件的记录：

1. App SQLite 中已有对应终态执行及事件收据；
2. Adapter 已持久化最终事件并收到 Relay ACK；
3. Relay 中不存在该请求或任务的待投递消息；
4. 终态已经超过保留窗口，且用户明确确认归档；
5. 归档摘要已写入业务数据库或可恢复备份。

归档协议采用“计划 → 各端验证 → 提交”的两阶段流程。任一端拒绝或断线时不删除任何去重信息。提交后保留最小墓碑：结构化来源身份、请求/任务 ID、最终序号、终态和归档批次哈希。墓碑用于拒绝旧请求和旧事件，不用于恢复正文。不得通过提高常量、清空文件或删除 watermarks 来恢复容量。

### 5.3 失败语义

- 核对失败：状态保持“待核对”，不转为 failed，也不自动重发；
- 容量接近上限：提前告警，不阻塞已有队列处理；
- 容量已满：拒绝新派发，继续完成和 ACK 已记录任务；
- 归档中断：未提交端全部保持原记录；已进入提交但回执丢失时，使用归档批次 ID 幂等重试；
- 旧事件在归档后重放：由墓碑确认已处理，ACK 后丢弃，不重新投影或执行；
- 墓碑容量达到上限：安全拒绝进一步归档，要求先生成备份并执行受控压缩迁移；不静默轮替。

### 5.4 Phase 5.1 验收

- 用户可区分执行中、待核对、离线、需授权和终态；
- 超时、重连、App/Relay/Adapter 重启均不产生第二个真实任务；
- 512/4096 边界附近的归档能恢复可用容量；
- 归档前后重放旧请求和旧事件均不重复执行或重复完成；
- 任一阶段故障不会留下“App 认为已归档、Relay/Adapter 仍不可恢复”的无说明状态。

## 6. Phase 5.2：版本化备份与事务恢复

### 6.1 备份类型

保留两种独立产物：

- **可分享导出**：沿用 `UserDataExportService` 的字段允许列表和脱敏语义；不可导入，不宣称可恢复；
- **私有恢复备份**：新建版本化 `.fgopetbackup`，用于同一用户或新机器恢复业务状态。

两者扩展名、界面文案、清单和代码路径必须分开。

### 6.2 备份内容

`.fgopetbackup` 至少包含：

- `manifest.json`：格式版本、应用版本、数据库 schema、创建时间、文件清单、大小和 SHA-256；
- `runtime.sqlite`：通过 SQLite backup API 或等价一致性快照生成，不复制活跃 WAL/SHM；
- `settings.json`：从模型重新序列化的允许字段快照；
- `packages.json`：已选择/引用的 package ID、版本和 appearance ID，只记录引用；
- 可选的归档索引与恢复说明，不包含角色资源正文。

备份必须排除：模型 API key、Windows Credential Manager 内容、Relay/Adapter 配对凭据、DPAPI 状态、绝对路径、开发日志、截图、构建物和角色包原始剧情资源。

### 6.3 创建流程

1. App 获取单实例维护锁，暂停新的业务写入和派发；
2. 对当前 SQLite 连接执行一致性快照；
3. 从内存中的有效设置模型生成允许字段快照；
4. 生成清单并校验每个成员的大小、哈希和路径；
5. 写入同目录临时文件，完成后原子替换目标；
6. 释放维护锁并恢复服务。

取消或失败时删除临时文件，不改变运行数据。

### 6.4 恢复流程

1. 在隔离 staging 目录解包，拒绝绝对路径、路径穿越、链接、重复条目、未知必需成员和超限内容；
2. 校验格式版本、哈希、SQLite 完整性和 schema 兼容性；未来版本只读拒绝，不尝试降级；
3. 在副本上运行受支持的数据库迁移和引用检查；
4. 将 `dispatching`、`active` 等非终态 Agent 执行规范化为“待核对/中断恢复”，保留请求与任务身份，不发出网络请求；
5. 验证设置和角色包引用；缺包不阻止恢复，启动后提示重新安装；
6. 为当前状态创建自动回退备份；
7. 获取维护锁，停止 App 业务写入及 Agent 投影，关闭数据库连接；
8. 使用同卷 staging/rename 交换数据库与设置；
9. 启动迁移器和核心服务，执行启动自检；
10. 自检失败则交换回旧状态，并保留失败报告和原恢复包。

恢复不会写入 Credential Manager，也不会恢复 Relay/Adapter 状态。跨机器或凭据缺失时，Agent 显示“需要重新配对”。

### 6.5 Phase 5.2 验收

- 从空目录 round-trip 恢复专注、时间线、羁绊、对话、记忆、Todo、执行、工作归档和设置；
- 损坏包、未来版本、超限包、部分写入、迁移失败和启动自检失败均不破坏旧状态；
- 备份中不存在凭据、绝对路径或角色资源正文；
- 活跃任务恢复后不会自动重执行；
- 恢复时缺少角色包不破坏已恢复数据，但首次使用门槛保持在角色包安装页，必须重新安装并激活角色包后才显示桌宠；模型和 Agent 插件仍可跳过。

## 7. Phase 5.3：配置引导

复用“设置 → AI 模型与连接”中的 Agent 区域，形成单一路径：

1. 检测 Relay/Adapter 安装与运行状态；
2. 安装缺失组件时展示将执行的本地变更并要求确认；
3. 显示待批准来源的可识别名称、实例和能力；
4. 从 Adapter 返回的目标目录选择项目，不要求复制不透明 ID；
5. 显式保存来源开关和项目 allowlist；
6. 提供连接测试、撤销、重新配对和诊断复制；
7. 卸载连接组件与清除业务数据保持分离。

默认仍为拒绝：未批准来源、未选择项目或已撤销权限均不能派发。不得提供“默认允许全部项目”快捷方式。诊断文本不得包含凭据、Prompt、对话正文或本地绝对路径。

**验收：** 普通用户不用修改 JSON 即可完成安装、批准、选择目标、测试连接和撤销；无插件时设置页不影响离线功能。

## 8. Phase 5.4：角色包与安装候选

### 8.1 角色包

- 以 main 当前 appearance/dialogue/persona/knowledge 合同为准，选择性整合 `feature/phase1-packaging-sdk` 的 art v3 和人工布局确认能力；
- Python builder 只接受数据和已审核素材，不允许可执行代码；
- 输入规范化顺序、时间戳、ZIP 属性和压缩策略固定，相同输入生成相同成员哈希和清单哈希；
- Python validator 与 .NET installer 共用合法/非法 fixtures，覆盖路径穿越、哈希错误、缺少必需内容、未知必需能力、版本不兼容和升级失败；
- 生成一份经过人工画像、透明边缘、锚点、裁切、表情和知识审核的玛修候选包；
- 程序与角色包分别构建、签名/校验和版本化。

### 8.2 程序安装

首版只承诺一个经过验证的 Windows/x64 范围和一种面向用户的安装路径。Release 交付物由一个用户级 GUI 安装包和至少一个独立 `.fgopetpack` 组成。用户双击安装包完成程序安装，不运行 PowerShell、CLI、构建命令或脚本。安装候选必须：

- 支持干净安装、覆盖升级、失败回滚和卸载重装；
- 首次启动进入角色包引导；必须选择、校验、安装并激活一个角色包后才能进入桌宠主界面，不提供“跳过角色包”；
- 模型和 Agent 均为可选能力，首次引导可以跳过，之后从设置页配置；
- GUI 安装包包含 App 以及 Release 所需的 Relay、Adapter 和插件注册载荷；Agent 未启用时不启动相关后台连接；
- Agent 安装、修复、插件注册、目标选择和卸载由安装界面或应用设置页调用受控内部服务完成，不要求用户操作 PATH、项目 ID、终端或脚本；
- 自动启动默认关闭，只有用户明确开启才写入；
- 卸载默认保留用户数据，数据清除是独立且二次确认的操作；
- 内部实现复用现有角色包导入器和 Phase 4 Adapter 安装逻辑，但脚本只保留为开发、诊断和验收工具，不作为 Release 用户路径；
- 不夹带配对状态、测试数据、生成目录、截图或用户备份。

**验收：** 候选包可重复构建并安全升级；用户只通过 GUI 完成程序安装、角色包导入和可选 Agent 配置；未安装角色包时不会进入空白桌宠主界面；安装角色包后可离线使用；升级失败可回到旧版本；程序发行物与角色资源完全分离。

## 9. Phase 5.5：试用与发行门禁

先以单个候选版本进行小范围真实使用，记录任务核对、容量、备份、配置、安装和日常操作中的具体失败。只修影响长期使用、数据安全和已承诺支持范围的问题。

候选冻结后统一执行：

- Release build 与全量 .NET/Python 测试；
- 角色包确定性和资源人工 QA；
- 干净安装、升级、失败回滚、卸载重装 smoke；
- 备份创建、空目录恢复和失败回滚；
- App/Relay/Adapter 重启、睡眠/恢复、去重和撤销；
- 凭据、路径、日志和发行物隐私检查；
- 明确支持范围内的 DPI、多显示器和长时间运行验收；
- 发行说明、安装/卸载/恢复指南和已知限制。

测试与人工验收分别记录。既有 Phase 1–4 证据可以复用，但任何被 Phase 5 改动影响的行为必须重测。不得把“代码通过”表述为“已公开发行”。

## 10. 依赖与交付边界

- 5.1 首先冻结任务身份、终态和归档墓碑语义；5.2 才据此定义活跃任务恢复规则；
- 5.2 的备份格式先于新增业务 schema，后续新增表必须同时进入 round-trip fixtures；
- 5.3 可在 5.2 后半段并行，但不得改变 5.1 的授权和去重语义；
- 5.4 的 SDK 合同梳理和素材审核可与 5.1/5.2 独立推进，builder 实现必须等待合同冻结；
- 5.5 只在 5.1–5.4 各自退出标准通过后开始候选冻结。

每个交付采用“设计确认 → 测试先行实现 → 核心评审 → 受影响测试 → 验收记录”。不按旧路线编号重跑已完成的 Phase 4 工作，也不一次生成整个 Phase 5 的实现计划。
