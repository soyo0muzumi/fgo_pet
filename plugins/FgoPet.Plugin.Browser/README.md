# Browser Plugin

`ChromeBrowserPlugin` contributes `browser.tabs`, `browser.open`, `browser.read`, `browser.click`, `browser.fill`, and `browser.inspect_image` to the existing Native tool registry. It connects on demand to a locally installed, pinned Chrome DevTools MCP **1.10.1**, using Node and stdio. It does not install software, launch another browser, change Chrome settings, replace the model runtime, or introduce an agent scheduler.

The host loads an explicit `chrome-browser.json` grant from its state directory. `ChromeBrowserSettingsStore` owns local setup reads and explicit settings-page writes. Its `Read()` result preserves valid disabled settings for editing and distinguishes missing configuration, disabled access, invalid JSON/paths, unreadable settings, missing runtime dependencies, and a missing profile directory. `SaveAsync` and `SetEnabledAsync` use cancellable atomic replacement, reject a concurrent configuration change, and renew `AuthorizationId` so a disable/re-enable cannot revive an in-flight grant. Advanced setup passes `enabled: null` to preserve the current enable state inside the writer lock, including a disable that occurred while the save was queued. Older valid files without that identifier remain readable. Changing the runtime/profile or disabling browsing revokes visual permission; initial setup never enables it.

The active-role/current-conversation check is repeated around protocol calls and before results are returned. Chrome's own remote-debugging connection approval remains required. This grant covers browsing in the connected profile for active conversations; it is not a per-site grant. Disable `Enabled` or disconnect in Chrome to withdraw access; an in-flight protocol call is bounded to 45 seconds, and changed authorization discards its result. Ordinary chat and offline capabilities remain available without Chrome.

Tools implement `IToolAvailabilityProvider`; readiness inspects only configuration and local dependencies and never reads tabs or initiates a connection. Ready means the setup can be used, not that Chrome is already connected. The optional `configurationError` host delegate supplies the same safe state codes to execution. The host-only `CheckConnectionAsync` and `ReconnectAsync` methods share the tool-operation gate, honor enabled grants and cancellation, and test `list_pages` without returning any tab titles, URLs or content. Reconnect resets only the owned MCP connection and snapshot cursors. Failed checks retain a safe connection/protocol error code; they do not change grants or retry a request.

The facade calls `list_pages`, `new_page`, `take_snapshot`, `click`, `fill`, and, when the browser grant includes images, `take_screenshot`. It rejects extra model arguments, credential-bearing URLs and non-HTTP(S) schemes. Opening a link creates a background tab and does not replace existing tabs. Browsing includes normal website loading effects, not a guarantee that arbitrary websites implement side-effect-free GET requests. No arbitrary selectors, script evaluation, file uploads, download-management tools, model-selected filesystem output, network-header inspection or generic DevTools tools are exposed. Clicks and input events can submit forms, navigate, trigger downloads or change website data. The server's telemetry, npm update checks, CrUX requests, JavaScript evaluation, file navigation and ambient configuration discovery are disabled. Existing page scripts still run normally in Chrome.

`browser.click(pageId, snapshotId, uid)` and `browser.fill(pageId, snapshotId, uid, value)` are `Command` tools. They require the existing native per-operation human approval; the browsing grant alone never authorizes an interaction. The confirmation shows the source URL, element description, input preview and full frozen arguments. Resource and business-confirmation bindings tie approval to the plugin lifetime, connection generation, host grant, scope, snapshot and exact operation. The latest `browser.read` snapshot for that page must be less than five minutes old and contain the UID. A new snapshot replaces prior handles for that page; reconnect invalidates all snapshots. The URL and authorization are checked before dispatch, and authorization again afterward.

`browser.fill` replaces an input's contents, supports empty text to clear it, and accepts at most 8,000 UTF-16 code units. It does not append a submit key, although website input handlers may have effects. Each dispatched interaction invalidates all cached snapshots; read again before the next operation. A successful result acknowledges the browser action, not completion of a business transaction. An error, cancellation or revoked grant after dispatch is `Unknown`; it must not be automatically retried. Upstream action text is discarded and entered text is excluded from result payloads and diagnostics. Frozen approval parameters remain in the existing approval flow.

The Web access page discloses text and screenshot access together. Explicitly enabling the browser grants both; an existing text-only grant remains text-only until the user selects Upgrade browser access. `VisualEnabled` remains in local settings to distinguish older grants and reject stale captures. `browser.read` returns a `snapshotId`; `browser.inspect_image` requires that recent scope-bound snapshot and page ID, optionally an image/element UID present in that snapshot. It captures the current viewport or rendered element, not an original URL image or full page; element capture may scroll it into view. The source URL and authorization are checked around capture. The existing connection is reused, with 1024×1024 screenshot bounds, JPEG quality 60 and low-detail model input. Inline captures must be below 2 MB and pass host decoding. Upstream file-only results are refused; server scratch files remain in an owned temporary directory cleaned when that connection closes.

Dialogue owns the in-memory image sink through Extensibility, binds one capture to the active scope, model route and run, refuses mixing with a user-selected attachment, and releases it on run termination. Revocation, scope/model changes and five-minute expiry prevent later dispatch. The run may send the same image more than once; the Buddy proxy may persist/re-encode it or retry upstream. Image bytes are not written into chat history or checkpoints. Captures are untrusted page evidence, never user-selected input or permission.

Page snapshots are untrusted tool observations. They retain URL, title, capture time, content hash and partial-read indicators. Text is chunked by Unicode scalar; cursors refer to an immutable in-memory snapshot scoped to the conversation, role, project and host grant. At most eight snapshots are retained, for at most five minutes of cursor access. A snapshot covers currently loaded accessibility content, not video/audio, the whole site, unloaded messages or long-term memory. Nothing here confirms a memory. Metadata diagnostics exclude URLs, titles, content, arguments and credentials.

`browser.read` defaults to, and is capped at, 8,000 Unicode scalars per call. Follow `nextCursor` for contiguous coverage; `offset`, `returnedCharacters`, `totalSnapshotCharacters` and `truncated` describe the actual portion returned. A successful call or final chat answer does not imply all snapshot segments were read. Native conversation runs reserve their last model request for a final answer with partial-coverage disclosure rather than offering another read.

Connection interruption closes only the owned MCP process and does not retry the failed request. The ReadOnly classification of browsing does not remove tab-creation or page-loading effects. Failed, unknown or incomplete opens can leave a newly opened tab; inspect `browser.tabs` before another open, and do not blindly reopen when verification is unavailable. Denied or revoked access is not a transient failure to retry. Protocol input, read sizes, process lifetime and output are bounded. Browser-consent prompts require the user; do not bypass them.

Build and test:

```powershell
dotnet build plugins/FgoPet.Plugin.Browser/FgoPet.Plugin.Browser.csproj -c Release -warnaserror
dotnet test tests/FgoPet.Capability.Tests/FgoPet.Capability.Tests.csproj -c Release --filter FullyQualifiedName~Browser
dotnet test tests/FgoPet.App.Tests/FgoPet.App.Tests.csproj -c Release --filter "FullyQualifiedName~BrowserApprovalIntegrationTests|FullyQualifiedName~NativeScenePolicyTests|FullyQualifiedName~Native_approval_card_displays"
```

The developer setup entry remains `tools/integrations/chrome-browser/setup.ps1`; installation and host activation are explicit operations. The application can supply bundled Node/MCP paths to `ChromeBrowserSettingsStore` from its settings page. Neither settings inspection nor connection checks install dependencies. See the integration's README for runtime preparation. Synthetic protocol and Native-loop tests are not real-browser/model acceptance.
