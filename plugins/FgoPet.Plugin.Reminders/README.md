# Reminders

This plugin owns one-shot local reminders, persisted with the existing runtime SQLite module-migration infrastructure. `reminder.create` and `reminder.cancel` use Native's exact business-confirmation path; `reminder.list` reports durable status in the current conversation/role/project scope. There is no new agent, execution-plan or Todo owner, recurring scheduler, model call, or permission bypass.

The production scene policy permits only these two reminder Commands and `focus.resume` to ask for approval; other native Commands stay denied. The approval card and separate native confirmation show the owner-frozen reminder text, offset time, named time zone and (for cancel) ID/revision. Allow is never accepted from model or WebView JSON. Decline, cancel, timeout and changed state do not grant permission.

A create binds the exact message (at most 255 UTF-16 code units, with well-formed Unicode, matching the Windows balloon capacity), explicit ISO-8601 offset, named time zone and scope. Invalid local times and offset/time-zone mismatches are rejected; an explicit offset resolves an ambiguous DST hour. Deadlines must be in the future and within 366 days. Cancellation binds the exact reminder revision and succeeds only before dispatch claims it. The visible production approval expires after five minutes; the owner also invalidates its private draft after ten minutes. Durable operation receipts prevent a repeated confirmed operation from creating a second reminder.

The worker checks every five seconds while the application runs, using the existing background-lifetime fence. Active foreground dialogue and maintenance can defer a check. UTC deadlines survive host time-zone changes, sleep and restart. Pending reminders at most 24 hours overdue are attempted once; older reminders become `expired`, rather than causing a stale notification flood. The application does not install an OS task, wake the computer or notify while it is closed. Synchronous container disposal and the process-stopping callback close admission and request cancellation without running notifier cancellation callbacks on the caller. Normal asynchronous shutdown awaits those callbacks and the same retained worker/explicit-pulse drain, even if a callback fails.

The Windows host submits a real system-tray balloon notification. `submitted` means the notification API returned, not that Windows displayed it or the user read it; notification settings and Do Not Disturb still apply. A crash after claiming, an exception with an uncertain external effect, or cancellation after an attempted dispatch becomes `unknown`, never an automatic retry. Definite notification unavailability becomes `failed`. The user can inspect these states with `reminder.list` and explicitly create a replacement when appropriate.

Reminders contain private conversation-linked action data. The existing explicit export/delete and backup-staging participant port includes them; deleting the source conversation or all dialogue data removes their bodies and receipts after the background lifetime drains. Restoring a private backup deliberately discards reminders in the staging copy, so old backups cannot re-arm notifications or resurrect deleted reminder text. The live database is never normalized in place. Logging contains only a hashed reminder identity, time, stage and safe error code.

Validation: `dotnet test tests/FgoPet.Plugin.Reminders.Tests/FgoPet.Plugin.Reminders.Tests.csproj -c Release`. Windows notification appearance, suppression and restart acceptance require a Windows desktop. Deterministic sink tests do not establish user-visible delivery.
