# Understanding P4 validation driver

Non-production, explicit-command test executable (`IsTestProject=true`). It composes the registered App services against fresh synthetic state and the independent durable trial ledger. It is not registered, packaged or started by the product. Production settings and private history are never written or imported. The default command is offline; network commands require the exact local human authority, approved route and immutable batch/trial registration.

The separately authorized `subscription-failures` command reruns only the 12 terminal failures from the closed repair manifest through the existing loopback Buddy gateway. `subscription-offline` first verifies its accounting/scope/replay/reopen boundaries and the same scenarios with synthetic HTTP. This path uses model capacity pinned to the installed adapter source and an explicit `ReviewRequestLimits`; it has no artificial trial/batch/total call ceiling. Every attempt is still durably recorded before HTTP handoff. Original fixtures, source validation, exact approval checks, timeouts, parallel configuration and closed v4 records remain unchanged. Short isolated temporary state directories have validated descriptors in the evidence folders. `subscription-review-ui RUN_ID TRIAL` reuses the actual approval page without model/credential services; `subscription-followup RUN_ID TRIAL` requires that exact new-version proof. Results are a separate experiment, never a rewrite of the closed v4 batch or automatic H1/H2 acceptance. Product settings and the default denied budget access are unchanged.

Runtime logs contain only hashed correlations, stages and safe error codes. Synthetic trial originals, proposals, exact provider inputs and outputs are separate local acceptance evidence, never product logs or default remote content. Semantic and UI acceptance belong to the human reviewer; a successful command cannot sign H2.

The separately authorized `subscription-formal-offline` / `subscription-formal` commands use all original 21 fixtures in a fresh, single-implementation batch. Live dispatch requires the full-batch protocol and a matching engineering evidence gate. The R3B seeded tests keep the original same-session followup and expiry check, with no review call. Formal followups recheck the frozen assemblies, protocol and engineering gate; exact-version human approval is still required for newly generated R1/R4 candidates. Earlier batches and approvals remain preserved and are never spliced into the new result.

The current host binds `formal-engineering-gate-v5.json` and the explicitly approved synthetic pending-draft authority. The earlier gates and binaries remain immutable evidence for their original runs. A matching gate proves the recorded offline engineering checks; channel availability and human semantic acceptance remain separate requirements. Subscription trial databases use the production default connection pooling, retaining the complete source, generation and cancellation checks for every streamed chunk. Each trial still has its own fresh synthetic database; the original closed official-channel host remains unpooled. Failure evidence includes inner exception types, fixed JSON issue categories, numeric offsets and method names; raw exceptions, JSON paths and response data are represented only by hashes. These diagnostics neither retry nor change a provider outcome.

Only the approved subscription host may invoke the existing `submit_todo_proposals` provider with `Proposal` effect. It can create a session-only pending draft; confirmation continuations and all other unrelated tools remain excluded. Todo source, persistence and production registration are unchanged. `subscription-proposal-offline` reproduces the observed denied-read batch followed by a pending draft through synthetic HTTP, checks an unrelated command canary remains uninvoked, and verifies that a confirmation utterance creates no Todo. Its test-only transport refuses live mode before host construction and never joins the 21 real trial results.

`subscription-retry RUN_ID` selects only terminal protocol failures from a prior Buddy run and starts fresh isolated attempts using the same original fixtures. The new run binds the previous manifest hash and selected IDs; completed trials, pending approvals and earlier evidence are preserved. A trusted subscription wrapper removes the ordinary primary request-count ceiling while retaining cancellation, deadlines, model capacity and source validation. Exact local Buddy Understanding auxiliary calls use the gateway's supported low reasoning effort under the original shared review/classification deadline.

Provider-required reasoning is omitted from saved input bodies; evidence retains its hash/byte count and the complete transport body's hash and pre-dispatch measurement. It is not persisted as conversation or review material.

`preregister` locks the formal fixtures and scoring before `offline-smoke` / `offline-formal` exercise the transport with synthetic credentials and HTTP only. `offline-faults` creates six owned child processes, stops each at an explicit synthetic boundary, kills only that child, and checks the durable ledger, preview and commit recovery after reopening. These results do not prove real model semantics.

`offline-reference-formal PYTHON WORKER ASSETS` runs the same 21 synthetic trials and ledger with the explicitly supplied, pinned local reference counter. The host pins worker bytes before process creation and the policy hash at startup. Replies, review and classification share the injected meter; unsupported auxiliary envelopes retain conservative estimation. It records only counter metadata separately from the existing synthetic acceptance evidence, and labels every accepted reference count with its immutable policy hash. The command never selects the live route or canonical ledger. A live host rejects any meter override before creating trial state or registering a trial; the offline command checks that refusal. Reference counts are local estimates, not provider usage or permission for another real batch. The shared pipe counter lives in `../token-meter-validation/PipeCounter.cs`; product composition remains unchanged.

Live `smoke` requires source, binary, regression and isolation evidence to match `engineering-gates.json`. `freeze` records the unchanged protocol, route and verified implementation after a successful current smoke run. `formal` executes all 21 independent trials; R1/R4 stop at concrete candidate packets. `review-ui TRIAL` opens only the actual Understanding page over that trial's synthetic database, with no model, HTTP or credential services. Closing it records exact approved revisions; a subsequent `formal` continues only those approved followups. Interrupted attempts stay charged and are not silently replayed. At most one separately frozen `repair` batch is supported under the same ledger and protocol.

Repair uses a separate immutable `engineering-gates-repair.json`; the original gate, frozen source archive, binary evidence, formal results and ledger snapshot remain preserved. It requires the original 21 trials to be terminal and uses the same preregistered material, scoring, route and cumulative ledger. UI proofs bind the exact approval packet, batch freeze and host assembly. The UI host defers disposal until the SettingsWindow close callback has returned; an actual UI failure remains a failed proof.

`smoke-review-repair` is a single explicit repair of the recorded BOUNDED JSON-mode precondition failure. It requires the two completed initial responses, the exact HTTP 400 classification failure, unchanged saved originals/policy and at least three calls left under the existing eight-call trial ceiling. It preserves the old result and database snapshot, repeats review/classification through the registered worker, then starts a fresh followup session. It cannot resume formal trials or an unknown/interrupted repair, refund charges, change fixture material or raise a limit. `offline-smoke-review-repair` verifies this path in a separate synthetic ledger with fake credentials/HTTP, keeping the canonical ledger read-only.

Only the explicit review caller's async flow receives the trial's review budget. The registered periodic worker still scans durable inputs, but cannot dispatch outside the controlled review window. Foreground replies, review, independent classification, summaries and tool continuations all share the trial ceiling. Full registered tool descriptors remain in the request; only Understanding and original-read fixture tools can execute. Persona is unchanged, provider metadata comes from the existing local catalog, and server revisions cannot be pinned.
