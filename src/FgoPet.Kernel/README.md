# Kernel

Pure .NET foundation for current role identity, user profile and character preferences, semantic companion presentation, conversation execution, context lifetime, and process shutdown. `AppRuntime` owns the active role; `CompanionPresentation` publishes neutral expression and text state. Context lifetime and shutdown coordination own their respective lifecycle boundaries.

ConversationOrchestrator owns turn admission, authoritative message persistence, capability coordination and completion. ConversationModelTurn owns one bounded model turn, stream aggregation, bounded attempts, tool downgrade and connection-change fencing. PromptComposer, input token metering, model capacity resolution, original-message recall and transactional summary planning compile here against published interfaces. Original messages remain authoritative; summaries and token anchors are rebuildable. Token anchors are process-local and invalidate on route, input, output reservation or request metadata changes.

Concrete HTTP request policy, SQLite repositories, settings UI and dialogue presentation remain in the Dialogue implementation. Installed package binding belongs to Content. Kernel preserves the existing public namespaces and constructor signatures; it has no WPF, concrete provider, SQLite or feature implementation dependency.

`IExperienceSourceReader` publishes a typed read of one authoritative completed original message with its owner scope, anchor, speaker and content version. Dialogue implements the storage lookup and hosts `experience.search/read`; Kernel does not query SQLite or create a second history/Understanding store. Missing, changed, out-of-scope and unavailable sources remain distinct outcomes.

`IExperienceTimeline` adds bounded fixed-version original-message windows with per-item scalar coverage, speaker and a Dialogue-owned monotonic source sequence. `IDerivedConversationData` lets derived-data owners participate in explicit privacy operations without exposing their repositories to the host. These ports do not dispatch models or enable automatic Review.

`IConversationScopeAuthority` publishes Dialogue's current role/project and active tool-scope validation. Scope consumers use that owner port; bootstrap does not own conversation selection or authorization logic.

`CompanionActivityCoordinator` owns bounded background judgments over host-supplied `CompanionContextSnapshot` observations. A meaningful source change can schedule work without a new user message; activity IDs are independent of conversation messages and Native runs. Notifications coalesce, unchanged attempts are not repeatedly dispatched, and the default minimum dispatch interval is five minutes within the coordinator lifetime. Background leases yield to foreground dialogue and participate in maintenance cancellation and drain. The host owns sampling, current source permissions, model configuration and persistence; Kernel does not read Windows state or create a second observation store.

`ICompanionActivityHost` revalidates exact scope, source versions, policy and model through the final dispatch and result-commit boundaries. `ICompanionActivityBudget` reserves an independent durable charge at provider handoff; dispatched, failed, cancelled or uncertain attempts are not refunded. `CompanionActivityModel` permits at most one model request per activity, offers no tools and defaults to 4,096 input / 384 output tokens. Production host approval is off by default and uses a separate rolling-24-hour allowance of six calls, adjustable to 1–24; it does not consume or enable the historical Understanding review ledger. Chat, memory extraction and this background allowance remain distinct.

The model receives bounded, source-labelled factual observations as data. Input limits can shorten or omit source material, so source identity or a successful response never attests a complete read. Result evidence is limited to the source material actually included in that request; coverage describes the bounded observation supplied, not all content in the original window or task source. Missing coverage attestation remains unknown. A temporary interpretation remains tentative and is projected only while the captured context, permissions, model and source versions remain current and unexpired; an older interpretation is not reused as fresh evidence. The activity does not publish unsolicited dialogue, execute tools or modify Memory or saved Understanding. Desktop Context owns the common ordinary/Native projection through the published context port; the host's source expiry can end usefulness before any configured result-lifetime ceiling.

Core persona and the active appearance overlay are mandatory, complete prompt blocks. History pressure returns an over-budget prompt to the existing compaction path rather than shortening character identity. A persona block exceeding the individual message limit fails explicitly; persona text is not automatically rewritten. Optional knowledge remains bounded.

A trusted provider wrapper may publish `IChatInputLimit` to lower the task's complete input ceiling. Ordinary and Native preparation constrain the existing input budget without changing provider capacity, output reservation, timeouts or tool contracts. Mandatory input that cannot fit fails before provider entry; optional whole data blocks that cannot fit even by themselves are omitted intact.

A trusted provider wrapper may publish `IChatRequestLimit` for the primary per-turn request count. The default remains three; an explicit null removes that count ceiling while cancellation, input capacity, protocol validation and Native run budgets still apply. The isolated subscription validation host opts in without changing product registration.

The shared input envelope serializes tool names through the existing request-local `ModelToolNameMap`. Registered canonical names, descriptions and parameter schemas remain intact; metering uses the same legal wire aliases as dispatch. Native requests that already carry aliases keep their existing wire representation.

Ordinary dialogue returns an active ReadOnly tool's result to the model when the capability supplies no conversation contribution. An all-read-only batch is validated in full before any member executes, uses the existing model-protocol batch limit and executes sequentially; mixed Proposal/Command batches retain whole-batch rejection. Each continuation retains complete call/result pairs and the original offered catalog, input/output limits and host request-count policy. Duplicate IDs, incomplete calls, cancellation and oversized results fail before a further dispatch; a read-only tool selection is not a completed assistant answer. Capability-owned replies and Proposal confirmation keep their existing owner paths; Command tools remain denied. Official DeepSeek reasoning needed for the current tool exchange is transport-only, included in input measurement and fingerprints, and absent from semantic-message serialization and persistence.

Native context assembly collects fresh authorized plugin data before compaction, measuring the complete host/tool/memory envelope. It retains provider, message and transcript hard limits; after compaction the loop validates the final input budget before dispatch. Auxiliary summaries share the run budget, so final-response reservation is checked again after preparation. Fresh context is not persisted into the working transcript and is collected again on the next step; current reviewed memory versions take precedence over historical references to the same memory.

Native history is projected once as source-labelled data attached to historical user turns. The same actual history cost participates in optional-background selection and final input measurement; the public legacy prompt-message limits remain unchanged.

`ConversationContextDiagnostics` uses the existing `ILogger` Debug channel at preparation, compaction and dispatch boundaries. It emits UTC time, hashed run/source identifiers, numeric memory versions/revisions, persona presence and token estimates by category, never prompt bodies or tool payloads. Category estimates include independent request envelopes and must not be added together. Disabled Debug logging performs no diagnostic measurement; diagnostic failures cannot fail a request. These are developer diagnostics, not a new Chat UI or a persistent content log.

`NativeAgentExtensions.ContextDiagnostics` is an optional operational observer for resolved capacity, independent envelope counts, compaction decisions and exact capacity rejection locations. Its typed contract carries only enum values and integer counts; Dialogue owns bounded persistence. An absent observer adds no diagnostic measurement. Observer or diagnostic measurement failures do not alter admission, compaction, execution or cancellation, and observations never imply HTTP dispatch.

An ordinary request rejected by the final input guard emits Warning event 4103 with UTC time, a fixed phase/error code, the actual rejected measurement and limit, count kind, message/tool counts, next attempt number and validated request hash. It reuses the guard's full-input measurement; it does not measure again, dispatch the rejected request or change the budget. Invalid hashes and diagnostic sink failures cannot expose content or bypass rejection.

`TokenCountKind.LocalReferenceEstimate` identifies a locally rendered/tokenized estimate with an optional reference policy hash, separately from conservative `Estimated` and exact-envelope `ProviderUsage`. Kernel does not load assets or start a reference runtime. Input guards use the returned complete count with the existing budget; the count kind grants no dispatch permission.

Every event published by an admitted `ConversationOrchestrator.SendAsync` carries one `ConversationUpdate.RequestId` (`request-` plus a GUID in N format). A trusted caller may supply a fresh GUID through the optional `requestId` argument before awaiting Send; otherwise the orchestrator creates it. The identity is captured in callbacks, including Native model stages, local replies, cancellation/failure and resumed Native delivery. It is not an authorization token. `ConversationId` can be reused across sends and `MessageId` identifies different messages, so neither replaces request correlation. Native `RunId` remains the durable execution identity returned in `ConversationSendResult`.

Production conversation runs allow 32 model requests and 64 tool calls per user send and opt into `RunBudget.ReserveFinalResponse`. These execution limits are separate from context capacity and per-request output tokens. Before the last available model request (or after exhausting the tool allowance), the loop removes offered tools and requests a final response grounded in existing observations, explicitly preserving partial coverage. A tool call in that final-only step fails without execution. Retries, compaction or an oversized batch can still exhaust hard limits; reserving a step is not an extra call or a guarantee that a provider will produce a valid answer. Other callers retain the default hard-budget behavior unless they opt in.

A changed model-connection revision cancels the active Native run whether the host fence or provider guard observes it first. Dispatched requests retain their charge. Scope/source failures remain fail-closed, and an uncertain started command retains `ExecutionUnknown` rather than being hidden by cancellation.

Native conversation separates tool selection from final output. A tool step offers a host-owned
`response.finalize` control call alongside available tools, without a final JSON template. The
tool-step instruction uses the control's actual wireName, requires calling it before answering,
and explains that the host will then issue a separate final-output request with no tools. The
control call must be alone, have empty object arguments and no answer text. It consumes the same
model/tool budgets and grants no business permission. It ends selection and starts a final request
with no tools; the fixed `text`/`emotion` template is appended after all other messages. If no tools
are available, the host can start directly in final output. Tool rejection can use the existing
no-tools fallback, whose actual request is final output. A tool-stage answer is rejected rather
than reused as a draft. Finalization control calls remain in the run journal but are omitted from
business history projections and from the final request's input; business call/result pairs remain.
An invalid finalization batch is discarded before any call is admitted. Once per run, if the
reserved final-response request remains available, the host can request a corrected control signal
with only `response.finalize` offered. The rejected text and calls are not reused as a draft or
executed. This correction uses the same input, durable request, cancellation and scope limits,
with no application-side transport retry or tool fallback. Only a valid control advances to the
normal final-output validator; an invalid correction retains `MODEL_INVALID_FINALIZE`.
A compliant final is delivered immediately, without another generation. When tools are offered,
selection can cost an additional request even if no business tool is needed; it never generates a draft answer.
Only a complete object with nonempty string `text` and no duplicate keys reaches delivery.
Omitted `emotion` defaults locally to `neutral` without a repair request; a present `emotion`
must be a supported string. Literal examples belong inside `text`; ordinary-chat compatibility is unchanged.
An invalid final uses the existing single format repair with no tools, the same durable budget,
and the existing cancellation and scope checks. The final template is last on repairs too, and
phase instructions and control schemas participate in normal input metering.

Host prompts identify the active persona as the desktop companion. Persona core and appearance text describe identity and expression without granting permissions or overriding host rules. The current user message is the turn's conversation or request; quoted material remains data. History, recalled sources, summaries and tool observations remain reference data rather than current instructions. All content envelopes escape delimiters and remain subject to the existing context budget and message limits.

Conversation recall enriches replies silently by default. Original-message recall, browsing and clarification require an explicit backward reference; current self-contained messages and questions about repeated clarification proceed to the normal reply. Clarification additionally requires multiple distinct selected candidates, an explicit ambiguity judgment, and a model-reported confidence of at least 0.85 for each selection. These scores are a conservative gate, not calibrated probabilities. Missing confidence or multiple search hits alone never trigger a history choice. Reference detection is deliberately conservative: unrecognized wording falls through to normal conversation.

`AgentRunCoordinator` provides a separately hosted native run loop: conversation admission, serial tool queues, bounded model/tool reservations, metadata events, cancellation and checkpoint compare-and-exchange. `IAgentRunStore` commits counters, intent, cursor and journal together; failed commits fence the writer. Completed step checkpoints retain bounded execution evidence separately from semantic conversation history. `IAgentModelStep` reserves each actual attempt through `IModelRequestBudget`. Typed skill, context and observer contributions are captured by the immutable plugin catalog; `AgentContextAssembler` applies provenance checks and measures assembled context through `IAgentModelInputBudget`. Tool execution commits intent before invocation and rechecks host resource authorization. Command tools default to denied without a host policy. Dialogue owns the protected SQLite run-state adapter, startup interruption closure and clarification UI. Action approval presentation remains deferred.

`NativeConversationRuntime` supplies the host admission owner to `ConversationOrchestrator`, preserving trusted scope and generation across waits. Summary calls share the durable Run model budget. Semantic history and private tool transcripts remain separate. Final publication uses the Dialogue acceptance ledger; waiting returns a Run ID and a waiting status rather than completion. Production registers the existing `UserInputBroker` and Dialogue's Chat bridge for `user.ask`; answering a question grants no action or source permissions. The host uses the existing scoped cancellation port when a visible clarification expires, without invoking the runtime's observation-and-resume expiry path. The host now registers the existing approval broker and a strict scene policy: only `reminder.create`, `reminder.cancel` and `focus.resume` may request exact per-call human approval. All other Commands remain denied; read-only and Proposal behavior is unchanged. The native confirmation UI is a separate host boundary, and a user.ask answer never authorizes a command. Normal shutdown awaits cleanup; synchronous container disposal signals cancellation without blocking the UI dispatcher.

Native protocol and runtime checks: `dotnet test tests/FgoPet.Agent.Tests/FgoPet.Agent.Tests.csproj -c Release`. Synthetic providers and effects do not establish real-provider or product UI acceptance. Durable delivery and recovery checks belong to Infrastructure and App tests.

Native provider output ending with `length` fails as `MODEL_OUTPUT_LIMIT`, including incomplete tool calls. Conversation delivery explains the output limit or exhausted run budget and suggests a shorter or smaller request; it never publishes a partial final or automatically replays tools.

Same-conversation sends project available terminal executions from the existing protected run store, scoped by role, project, conversation and original user message. A `historical_execution` data block is attached to its historical user turn; old runs no longer generate assistant tool calls or tool-role messages. Oversized evidence is split into contiguous data fragments identified by root message and character offset, preserving the existing per-message limit before compaction; fragments do not truncate facts or increase the context budget. Original call IDs, arguments, results, statuses, timestamps and source identifiers remain evidence, never queued work. `Project` and `DescribeTools` share fact serialization for direct model input and summary input. Missing results remain explicitly unknown/unexecuted, and `approvalEvidence=NotIncludedInThisProjection` states that approval information is omitted from this projection; it makes no claim that approval or stored records are absent. Current runs keep their real call/result protocol, including completed steps and resumed waits. Storage, restart closure and semantic Chat messages are unchanged; intermediate assistant prose is not reconstructed. This does not confirm long-term memories or grant tool permissions; a current page may still need rereading to check freshness.

Historical observation metadata distinguishes the tool call's `historicalStatus` from the enclosing historical run's `runStatus`. A completed run can contain a failed tool call; `noObservation=false` means a result record exists, not that its requested fact was found. Run timestamps are projected in UTC while preserving their instant and missing completion times. The Native host rules keep these execution times separate from dates in source material and require an explicit known target timezone for conversion; they guide model interpretation and do not guarantee semantic correctness.

`NativeAgentEnvironment.CorePrompt` is the single Native execution-rule body, injected once per step and reserved during prompt preparation. `PromptComposer` retains Persona, output format and background composition; its ordinary-chat safety rules remain on the ordinary path. Embedded skills own business workflows, source coverage and owner-specific confirmation/state requirements. General approval, retry and idempotency rules belong to the Native host. New approval or call IDs cannot resolve an unknown prior effect; this consolidation introduces no cross-run command recovery.

Native requests include a host-owned table mapping each actually offered tool's canonical name, wire alias and effect. The same projection is included in token measurement and dispatch; no table is added when tools are absent or downgraded. Optional background selection reserves currently offered tool definitions and contract metadata; per-step admission remains authoritative. Dispatch diagnostics measure the projected request without adding that metadata again. Tool descriptions and parameter schemas are preserved by this projection. This table describes registration, not authorization, service configuration or approval readiness. Loaded skills add workflow instructions, not execution permissions. Command execution requires exact host approval and any business confirmation required by its owner; Proposal only submits a pending draft.

When a native model step includes a resolved `skill.load` and the skill loader is available, only the first load in that batch can execute. All sibling calls, including earlier calls and additional loads, receive `NotExecuted` with `TOOL_DEFERRED_FOR_SKILL_LOAD`; their original IDs remain paired with observations. Loaded instructions enter the next model request, where the model must reconsider business calls and issue fresh IDs. Siblings are not replayed automatically, including after a failed load. Requests still consume the existing tool-call budget even when deferred; a low budget may stop the batch before loading or before another model request. Approval, checkpoint format and restart recovery rules are unchanged.

Retry guidance distinguishes unknown command outcomes, effects already committed despite missing output, and known failed read-only operations. `success` and `executionState` are independent: failed output with `Committed` does not authorize replay, and `NotExecuted` does not grant permission. Host idempotency keys identify one run/step/call; a fresh call gets a different key, and the model has no old-key or same-operation replay API. Receipt recovery uses an offered read-only query or reports the missing receipt. A known read failure can allow a fresh user-requested read within current permissions, budgets and tool-specific recovery rules; ReadOnly does not guarantee absence of incidental effects. Historical metadata carries the recorded `toolEffect`; missing values remain unknown rather than being inferred from current registration or source text. These instructions add no automatic retry or execution authorization.

Final reply validation repairs only a single whole `data` shell whose sole source matches the internal delivery shape and whose body contains the host data preamble or a complete `text`/`emotion` reply object. Recognized sources are 32/64 hexadecimal delivery IDs (optionally prefixed by `history/source:`) and the exact `delivery-current:Assistant` alias; arbitrary delivery names are not inferred. It does not recursively strip markup or interpret recovered memory/feedback fields. Quoted/fenced/inline examples, mixed prose, ambiguous/nested markup and literals present in the current user message remain data. Complete JSON examples followed by prose retain that prose; incomplete legacy replies can recover only a top-level text string. Native durable acceptance still rejects genuinely incomplete JSON replies. Ordinary and Native delivery supply the current user text, and Dialogue revalidation uses the scoped, fingerprint-verified root source. The original two-argument validator entry remains available. This is bounded format recovery, not a general HTML cleaner or a guarantee about ambiguous unmarked historical quotations.

`ConversationSummaryService` also summarizes tool evidence. Completed historical turns use the existing summary projection and transactional coverage watermark. During a run the same service creates only a working-context projection; it never advances the watermark past the live user message. Compaction triggers near the existing token threshold or 512 KiB working-context size, preserves complete call/result groups and the current user/latest group, and charges the same model-request budget while reserving a final request. Source text is split by position to fit summary requests; failed or cancelled compaction leaves the projection unchanged. Production no longer silently drops old groups to fit. Protected originals remain under the store's existing retention/quota policy, not unlimited archival. A single oversized message or tool batch can still hit the unchanged protocol/transcript limits and fail explicitly.

Portrait rendering is a provider capability: Kernel exposes `IPortraitBackend`/`IPortraitController` contracts. The Kernel references Extensibility, which publishes Platform contracts, and standard logging abstractions.

Validation: run the relevant Kernel, Dialogue, Windows, and EndToEnd test projects under `tests/`, plus the architecture gate for dependency changes. These checks do not replace real-provider or device acceptance.

Each ConversationOrchestrator send captures one immutable RequestId for its event publisher, including Native and local capability replies. Callers may supply the GUID before starting a send; events never derive their identity from mutable current-request state. This identity is presentation correlation, not authorization or persistent run identity.

Native final answers pass the same strict structured-output validator used by durable delivery before the run is completed. A malformed final may receive one format-only model correction with no tools offered; it uses the same durable request budget, connection and active-scope checks, input limits and cancellation. A second invalid final or tool call fails the run before acceptance. The host does not guess JSON repairs, replay tools, or weaken the delivery store. Native user literals belong inside the JSON text field; ordinary chat retains its existing plain-text compatibility.

Current tool observations carry checkpoint-owned source identity, call status and recorded Effect. Historical calls remain historical data; successful receipt lookup describes the query, not successful execution of its target. Missing Effect remains null, payload cannot replace the outer metadata, and clarification results do not acquire approval evidence.

Selected-image contracts retain only opaque references in native tool observations. `SelectedImageStore` enforces one expiring, exact-scope and exact-route grant tied to an original desktop message and one native run. Granting requires that persisted message ID; context binds the run once, and tool reads reject another or missing run ID. Clear/reselection and the final synchronous HTTP handoff share a dispatch lease. `IChatImageInputProvider` explicitly opts into request preparation before budgeting. Prepared PNG data lives only in request-local weak state, not semantic messages or run checkpoints. The envelope preserves complete tool batches before adding one user image part; the conservative meter reserves 8,192 image tokens without treating base64 as text, while exact provider usage still takes precedence. This reserve also covers the official DeepSeek Flash documented 1,024-token image ceiling; the text-only local reference counter must not replace it for image requests. Historical source projections do not restore image references. Tests: `dotnet test tests/FgoPet.Agent.Tests/FgoPet.Agent.Tests.csproj -c Release`.

`ImageModelCapabilities` additionally recognizes only the exact local Buddy tuple: provider `custom-openai-compatible`, base endpoint `http://127.0.0.1:8326/v1`, model `buddy/deepseek-v4.1-flash`. This is a capability declaration, not service authentication or a credential. Existing provider/model/endpoint/configuration and session bindings remain authoritative; unknown proxy routes are denied. The application-owned in-memory snapshot does not imply that a downstream proxy or model retains no copy.
